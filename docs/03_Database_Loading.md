# Database Loading

## 1. Назначение

Данный документ описывает процесс загрузки данных в проекте **Study Recommendation System**.

Загрузка выполняется через промежуточный **staging-слой**, который используется для проверки качества данных перед их переносом в основные таблицы базы данных.

Такой подход обеспечивает воспроизводимость процесса загрузки, позволяет обнаруживать ошибки до их попадания в рабочую базу данных и упрощает дальнейшее развитие проекта.

### Связанные документы

Данный документ описывает процесс загрузки данных в проект.

Подробная информация о других компонентах системы приведена в отдельных документах:

# 2. Общая схема загрузки

Данные проходят последовательный путь от исходных Excel-файлов до аналитических представлений и рекомендательной системы.

Каждый этап выполняет отдельную функцию и завершается до начала следующего, что позволяет обнаруживать ошибки ещё до их попадания в рабочую базу данных.

# 3. Почему используется staging

Загрузка данных непосредственно в основные таблицы была бы возможна, однако такой подход существенно усложнил бы контроль качества данных.

Использование промежуточного слоя позволяет:

- проверить данные до загрузки;
- обнаружить дубли;
- проверить обязательные поля;
- выявить неизвестные паттерны;
- проверить возможность последующей загрузки без нарушения ссылочной целостности;
- безопасно повторно загружать данные после изменения словаря или банка задач.

Кроме того, использование промежуточного слоя делает процесс загрузки воспроизводимым и позволяет повторно выполнять его при изменении исходных данных.

# 4. Pipeline загрузки

Процесс загрузки состоит из нескольких последовательных этапов.

Каждый этап выполняется последовательно и является обязательным.

Переход к следующему этапу возможен только после успешного завершения предыдущего.

## Шаг 1. Очистка staging-таблиц

Перед импортом данных все raw-таблицы очищаются.

```text
dictionary_raw
tasks_raw
attempts_raw
task_bank_raw
```

Это исключает влияние предыдущих загрузок и обеспечивает воспроизводимость процесса.

---

## Шаг 2. Импорт из Excel

Данные импортируются в соответствующие staging-таблицы без предварительных преобразований.

Каждый источник данных загружается независимо.

| Источник | Таблица |
|----------|---------|
| Dictionary | `dictionary_raw` |
| Tasks | `tasks_raw` |
| Attempts | `attempts_raw` |
| Task Bank | `task_bank_raw` |

---

## Шаг 3. Проверка качества данных

После импорта выполняется автоматическая проверка данных.

Контролируются:

- обязательные поля;
- дубли;
- корректность диапазонов значений;
- неизвестные паттерны;
- соответствие словарю;
- полнота банка задач.

При обнаружении ошибок загрузка в основные таблицы не выполняется.

---

## Шаг 4. Загрузка в production

После успешного прохождения проверок данные загружаются в основные таблицы.

Во время загрузки выполняется:

- преобразование `pattern → pattern_id`;
- заполнение внешних ключей;
- проверка ограничений (`CHECK`, `FOREIGN KEY`).

---

## Шаг 5. Финальная проверка

После завершения загрузки выполняется контроль целостности данных.

Проверяются:

- количество записей;
- корректность внешних ключей;
- отсутствие потерянных записей;
- успешная загрузка банка задач.

---

# 5. Структура SQL-проекта

Для повышения воспроизводимости процесса загрузки SQL-скрипты разделены по этапам выполнения.

| Файл | Назначение |
|------|------------|
| `01_drop_tables.sql` | Удаление существующих объектов |
| `02_create_tables.sql` | Создание основных таблиц |
| `03_create_raw_tables.sql` | Создание staging-таблиц |
| `04_validation.sql` | Проверка данных перед загрузкой |
| `05_load_main.sql` | Загрузка основных таблиц |
| `06_final_checks.sql` | Финальная проверка |

Отдельный набор скриптов используется для банка задач.

| Файл | Назначение |
|------|------------|
| `07_create_task_bank_raw.sql` | Создание staging-таблицы банка задач |
| `08_task_bank_validation.sql` | Анализ и проверка данных |
| `09_create_task_bank.sql` | Создание основной таблицы банка задач |
| `10_load_task_bank.sql` | Загрузка банка задач |
| `11_task_bank_checks.sql` | Финальная проверка |

Разделение процесса на независимые скрипты позволяет повторно выполнять отдельные этапы разработки, упрощает сопровождение проекта и делает структуру репозитория более понятной.

# 6. Архитектурные решения

При проектировании процесса загрузки данных было принято несколько ключевых решений.

## Полная пересборка базы данных

На текущем этапе проект активно развивается: регулярно изменяется словарь знаний, добавляются новые задачи и пересматривается их классификация.

Поэтому используется стратегия полной пересборки основных таблиц после изменения исходных данных.

При небольшом объёме информации такой подход значительно упрощает сопровождение проекта и позволяет избежать накопления несогласованных данных.

После стабилизации структуры проекта планируется переход к инкрементальной загрузке.

---

## Использование словаря как единого источника знаний

Все связи строятся через таблицу `dictionary`.

Во время загрузки текстовые значения `pattern` автоматически преобразуются во внутренний идентификатор `pattern_id`.

Это обеспечивает единообразную классификацию знаний и исключает дублирование информации.

---

## Разделение источника данных и аналитической базы

Исходные данные хранятся в Excel и рассматриваются как **Source of Truth**.

PostgreSQL используется исключительно для хранения, анализа и формирования рекомендаций.

Такое разделение позволяет независимо изменять структуру базы данных и содержимое учебных материалов.

---

# 7. Возможности развития

Текущая версия процесса загрузки ориентирована на ручное обновление данных из Excel.

По мере развития проекта процесс может быть автоматизирован.

Планируемые направления развития:

- загрузка данных с использованием Python;
- автоматическая генерация отчётов о качестве данных;
- инкрементальная загрузка вместо полной пересборки;
- оркестрация ETL-процесса с помощью Apache Airflow;
- интеграция с внешними источниками данных.

Благодаря разделению процесса загрузки на независимые этапы большинство из перечисленных изменений может быть реализовано без изменения структуры основных таблиц и аналитического слоя.
